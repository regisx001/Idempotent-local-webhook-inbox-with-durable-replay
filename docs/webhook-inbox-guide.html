Idempotent Local Webhook Inbox

A complete guide to resolving duplicate, out-of-order, and conflicting webhook retries with monotonic versioning, strict isolation, and atomic file-state persistence.

CORE INVARIANT 1

Two-Tier Verification

  • Delivery Gate: Evaluates incoming delivery identity. Checks: "Have I seen this ID before?"
  • Entity Gate: Evaluates domain state freshness. Checks: "Is this version newer than what I know?"
  • Separation: An existing delivery stops before version checks; a new delivery registers its ID even if stale or conflicting.

CORE INVARIANT 2

Monotonic Findings

  • Never decrease: Finding versions only increment (v1 → v2 → v3).
  • Lower version: Silently marked stale; finding remains intact.
  • Equal version: Same status yields redundant; conflicting status yields rejected.

CORE INVARIANT 3

Atomic State Durability

  • Directory Atomicity: Write state to a temp file in the same directory, then perform atomic rename/replace.
  • Crash Invariance: A failure mid-write preserves the old state untouched.
  • Corrupted State: Malformed state aborts the run with exit code 2 without mutating bytes.

1. What You Should Do, in Order

Follow this exact sequenced implementation roadmap to satisfy the candidate acceptance criteria without over-engineering.

  • Step 1: Confirm the baseline. Run the initial tests and the starter command:
    python3 -m unittest discover -s tests -p '*_test.py' -v
    python3 app.py --input inputs/primary.json
    Expect exit code 3 on the starter command. The smoke suite will pass. Verify arguments --input, --tenant, and --state are available.
  • Step 2: Write validation first. Implement two validators:
    1) Row validator: Ensure delivery_id, tenant, and finding_id are non-empty strings after trimming. Validate that version is a strictly positive integer, guarding against isinstance(True, int). Ensure status is exactly open or resolved. Check tenant matching against CLI --tenant.
    2) State validator: Validate JSON structure containing tenant (matching CLI), deliveries (dict), and findings (dict). Absent state file = fresh empty state. Corrupted/invalid state = exit code 2 immediately!
  • Step 3: Implement the per-row decision engine. Maintain in-memory state objects for deliveries and findings. Process delivery rows strictly in order. Implement the 7 decision steps:
    • Step 1: Invalid/Foreign → rejected (do not store key).
    • Step 2: Existing delivery_id in state: compare canonical payloads {tenant, finding_id, version, status}. Same → duplicate; Different → rejected.
    • Step 3: New delivery_id: immediately record canonical payload in state.
    • Step 4: Compare version with finding: absent finding or version > current → applied (mutate finding state).
    • Step 5: version < current → stale.
    • Step 6: version == current and status == current → redundant.
    • Step 7: version == current and status != current → rejected (version conflict).
  • Step 4: Implement atomic state persistence. Only write state if processing completes successfully. Write to Path(state_path).with_suffix(".tmp") in the same folder, flush, and call os.replace(temp_path, state_path). On write errors, exit with code 2.
  • Step 5: Reproduce the three verification runs. Execute the verification runs against a fresh state file (e.g., scratch-state.json):
    1) Primary run 1: applied 3, duplicate 1, stale 1, redundant 0, rejected 4
    2) Primary run 2 (replay): applied 0, duplicate 6, stale 0, redundant 0, rejected 3
    3) Secondary run: applied 2, duplicate 0, stale 0, redundant 1, rejected 0
  • Step 6: Write rigorous feature tests. Replace the starter placeholder test. Cover:
    • Boundary case: version: true rejected without reserving key.
    • Whitespace trimming: " d1 " and "d1" treated as duplicate.
    • Corrupted state byte immutability: assert bytes of invalid state file are unchanged after run, exiting with code 2.
    • Fixed flaw documentation: document at least one concrete failing case fixed during development.
  • Step 7: Finalize assessment deliverables. Produce the run guide, decision/work log, AI-use note, and text walkthrough.

Why the Second Run Produces 6 Duplicates and 3 Rejections

State saved after Run 1 contains delivery IDs d1, d2, d3, d6, d7 and findings f1: {v3, resolved}, f2: {v1, open}.

When primary.json is replayed against this state:

  • Rows 1, 2, 4, 5, 8, 9 have existing stored IDs matching their payloads → 6 duplicates.
  • Row 3 conflicts with stored d1 → rejected.
  • Row 6 (tenant south) is foreign → rejected.
  • Row 7 (v0) is invalid → rejected.

Result: applied 0, duplicate 6, stale 0, redundant 0, rejected 3.

3. The Traps & How to Guard Against Them

Trap / Edge Case Risk / Consequence Prevention Pattern
Row 9 rejection vs storage Assuming all rejected rows are discarded from state Store new valid delivery keys immediately in Step 3. Version conflicts (Row 9) remain permanently recorded so replays detect them as duplicates.
Invalid key reservation Storing an ID from a malformed row (e.g. d5 with v0) Only store after full schema validation and tenant checks pass. Never reserve an idempotency key for invalid rows.
Boolean is int in Python isinstance(True, int) == True allows "version": true Check type(version) is int and not isinstance(version, bool) and version > 0.
Untrimmed whitespace " d1 " and "d1" treated as separate keys Trim all string fields (delivery_id.strip(), tenant.strip(), etc.) before lookups or storage.
Canonical payload equality Comparing unnormalized dicts or raw rows Normalize canonical payload to exactly {tenant, finding_id, version, status} with trimmed strings.
Mid-run state propagation Row 2 ignoring mutations made by Row 1 Process sequentially in order, updating in-memory state dictionaries synchronously after each row.
State write atomicity Partial writes on process termination corrupting state Write to a temporary file in the same directory as the target state file, then execute os.replace().
Corrupted state file Overwriting an unreadable state file with empty data Validate existing state schema on startup. If unparseable or tenant mismatch, exit 2 immediately and do not touch the file.
